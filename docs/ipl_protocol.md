## 1. Entering IPL mode (boot code)

Reset vector = 0x000810 [VERIFIED: vector table word 0]. Sequence [VERIFIED: 0x810–0x8C4]:
SP=0xFFFC00, EXR=0x7F, bus controller / MSTPCR (0x5D9F) / SYSCR=0x21, port init (0x8C8), clear on-chip RAM 0xFFF400–0xFFFBFF,
`jsr 0xA18` (TPU register init), `jsr 0xBFA` (panel scan), `jsr 0xCA0` (classifier). If the classifier returns:
`jsr 0x02049A; jmp 0x002000` (normal firmware). **No checksum or integrity check of the firmware is done before this.** [VERIFIED: 0x8B4–0x8C4]

Panel scan 0xBFA: for col = 0..7: P5DR low nibble = col, ~0x190-iteration delay, `PORT6 (0xFFFF55)` → RAM 0x4027D6+col.
Switches are active-low. [VERIFIED: 0xBFA–0xC9E]

Classifier 0xCA0 (c[n] = column byte) [VERIFIED: 0xCA0–0xD50]:

| Condition (all of: `c0|1 == 0xFF`, i.e. c0 bits 7..1 released, bit 0 ignored; c1=c3=c5=c6=0xFF) | Result |
|---|---|
| c4 == 0xFD (c4 bit1 = WRITE) and c2 == 0xFD (c2 bit1 = TYPE) | IPL, mode 0 |
| c4 == 0xFD and c2 == 0xFB (c2 bit2) | IPL, mode 1 |
| c4 == 0xFD and c2 == 0xF7 (c2 bit3) | IPL, mode 2 |
| c4 == 0xFE (c4 bit0) and c2 ∈ {FD,FB,F7} | `jmp 0x22CCA` with r0 = 0/1/2 — a service mode inside the main firmware (not analysed) |
| otherwise: AND(c0..c6) == 0xFF | IPL, mode 2 |
| otherwise | normal boot |

The "AND == 0xFF" case: on a healthy panel diode D51 ("for version up", no switch) pulls c0 bit0 low permanently, so
the AND is 0xFE and the unit boots normally; an all-0xFF matrix means a dead/disconnected panel scan, which forces IPL mode 2.
[VERIFIED: code; the D51 explanation is from our emulator notes h8s2350_emulator.h:1655 — INFERRED for real hardware]
Key names: c4 bit1 = WRITE, c2 bit1 = TYPE per unknown's README/emulator [INFERRED]; the keys at c2 bit2 / bit3 [UNKNOWN].

IPL launcher at flash 0x1CB2 (= RAM 0x407F5E, it sits inside the IPL image) [VERIFIED]:
```
if (mode > 2) mode = 2
jsr 0x48A                         ; copy flash 0x200..0x48B -> RAM 0x400000 (flash library)
eepmov.w  0x1083 bytes  flash 0xD54 -> RAM 0x407000   ; count is the word at flash 0x1CCE
jmp 0x4070F0                      ; r0l = mode
```
0x407000 is a second entry with full CPU init (sets SP, bus, ports); nothing in the 256 KB image references it. [VERIFIED: byte search]

Mode → SCI1 BRR [VERIFIED: 0x407186–0x40719A]; SMR1 is not written (reset value 0 = async 8N1, φ/1);
SCR1 = 0x30 (TE|RE, no interrupts) [VERIFIED: 0x407206]. With φ = 10 MHz [INFERRED from our emulator; consistent with MIDI]:

| mode | BRR | baud | probable use |
|---|---|---|---|
| 0 (WRITE+TYPE) | 9 | 31250 | standard MIDI — **use this** |
| 1 | 7 | 39062.5 | KORG updater "serial transfer" at ComBaudRate=38400 (+1.7 %) [INFERRED from vup_ms2000.ini] |
| 2 (incl. dead panel) | 4 | 62500 | [UNKNOWN] factory jig |

IPL init (0x4070F0) [VERIFIED]: clear LED tables, LCD init, LCD row 1 `IPL s.p.u [    ]`, row 2 `................`,
mode LED, clear variables (0x406033 = 4 = "no type"), TPU ch2: TGRA = 2500, TCR = 0x29 (φ/4, clear on TGRA) →
1 ms tick at φ = 10 MHz [INFERRED φ], start TPU2, clear SCI1 errors.

## 2. IPL main loop and SysEx state machine

The IPL is a single polled loop, no interrupts used [VERIFIED: 0x407222–0x407334]:
```
loop:
  tick()                                   ; 0x40788C, runs its body once per TPU2 TGFA (1 ms)
  if (SSR1 & 0x38) goto sci_error          ; ORER|FER|PER
  if (SSR1.RDRF) { b = RDR1; clear RDRF
      if (b >= 0xF8) continue              ; realtime bytes ignored in every state
      jmp state_table[state & 0x0F](b) }   ; table 0x407FA8
  else if (SSR1.TDRE && txcount) send txring[txhead++ & 0xFF]
```
Consequence: while the IPL is busy (blank scan, erase, program) nothing is received; a byte arriving then causes an
overrun → `hrd` error. **The host must wait for each reply before sending the next message.** [VERIFIED/INFERRED]

State table (0x407FA8) [VERIFIED]:

| state | handler | accepts | next |
|---|---|---|---|
| 0 | 0x407338 | F0 | 1 (any other byte silently ignored) |
| 1 | 0x407340 | 42 | 2 |
| 2 | 0x407348 | 23 | 3 |
| 3 | 0x407350 | 58 (stored in 0x406032) | 4 |
| 4 | 0x40735E | command 0..7 → `jmp @cmd_table[cmd]` (0x407F88) | per command |
| 5 | 0x40737E | type 0..3 → 0x406033 | 11 (action 2) |
| 6 | 0x40739A | block number, must be < nblocks[type] | 7 |
| 7 | 0x4073C2 | 00 (block number high 7 bits) | 8 |
| 8 | 0x4073CE | first packed data byte (<0x80); resets offset/remaining=0x2000/sum/unpack | 9 |
| 9 | 0x407404 | packed data bytes (<0x80) until 8192 bytes unpacked | 10 |
| 10 | 0x40743E | checksum byte | 11 (action 3) or `sum` error |
| 11 | 0x407458 | F7 → `jsr @f7_action[action]` (0x407FD8), then state 0 | 0 |

Any unexpected byte in states 1–11 → **format error** (0x40730E): state 0, LCD `fmt`, reply `03 01`, type := 4. [VERIFIED]
Note the header is fixed: byte 2 must be 0x23 (no MIDI channel), byte 3 = 0x58 (MS2000 ID).

Command table (0x407F88) [VERIFIED]:

| cmd | entry | meaning |
|---|---|---|
| 0 | 0x407376 | version request (F7 action 1) |
| 1 | 0x40730E | unused in v1.07 → format error (fwpatch: flash dump) |
| 2 | 0x40737A | set update type (F7 action 2) |
| 3 | 0x40730E | unused → format error |
| 4 | 0x40738C | data block (F7 action 3) |
| 5,6,7 | 0x40730E | unused → format error |
| ≥ 8 | — | format error |

**Error latch:** reply_status (0x407858) stores its code in 0x406038. If 0x406038 ≠ 0, a cmd 4 (data) message is
**silently discarded** (state 0, no reply) [VERIFIED: 0x40738C]. Only a successful Set-Type or a successful block write
stores 0 again. While 0x406038 ≠ 0 the tick routine also queues a **0xF8 byte every 2 ms** (every 2nd 1-ms tick)
[VERIFIED: 0x407936–0x40794A; timing INFERRED from φ]. The host must ignore realtime bytes.

### 2.1 Messages host → MS2000

| Message | Bytes |
|---|---|
| Version request | `F0 42 23 58 00 F7` |
| Set update type | `F0 42 23 58 02 tt F7`  (tt: 0 SYS, 1 PCM, 2 USR, 3 ALL) |
| Data block | `F0 42 23 58 04 bb 00 <9363 packed bytes> ss F7`  (9372 bytes total) |
| (patched IPL only) dump | `F0 42 23 58 01 a2 a1 a0 am n2 n1 n0 nm F7` — see §6 |

### 2.2 Messages MS2000 → host

| Message | Bytes | Sent by |
|---|---|---|
| Version reply | `F0 42 23 58 01 SL SH PL PH UL UH F7` | 0x40780A [VERIFIED] |
| Status reply | `F0 42 23 58 03 cc F7` | 0x407858 [VERIFIED] |
| Heartbeat while error latched | `F8` every ~2 ms | 0x40794A [VERIFIED] |

Version words (low byte first, **not masked to 7 bits**) [VERIFIED: 0x407816–0x40784E]:
S = word @0x000804 if byte @0x000807 == 0 else 0; P = word @0x040004 if byte @0x040007 == 1 else 0;
U = word @0x0A0004 if byte @0x0A0007 == 2 else 0. Word = major<<8 | minor, e.g. v1.07 → `07 01`.
Order is **System, PCM, User**. (fwdump main.c and KORG's own log string label bytes 7–10 as "User / PCM"; KORG's
version *comparison* uses bytes 7–8 for a PCM file and 9–10 for a USR file, matching the firmware. [VERIFIED: vup 0x4032C0, 0x4032AE])

Status codes [VERIFIED: all 6 callers of 0x407858]:

| cc | LCD | cause | location |
|---|---|---|---|
| 00 | — | OK (after Set-Type and after every block written) | 0x407510, 0x407750 |
| 01 | `fmt` | bad byte / unknown command / bad type / block out of range / Set-Type with invalid type | 0x407542 |
| 02 | `sum` | checksum mismatch | 0x407306 |
| 03 | — | **never sent by v1.07** (vup/fwdump know it as "Timeout") | — |
| 04 | `hrd` | SCI receive error (overrun/framing/parity), or data block F7 with no valid type | 0x407566 |
| 05 | `wrt` | erase or program failure | 0x407696 |

Every error except 04 also sets type := 4; 04 via the SCI path also sets type := 4. The reply is queued after a
~0x7D-iteration delay. The IPL has **no receive timeout of its own**. [VERIFIED]

## 3. Update transfer in detail

### 3.1 Update types (tables at 0x408008/0x408010/0x408014) [VERIFIED: 0x40748A–0x4074DA]

| tt | name | first 8K block | nblocks | flash range | sector mask (64K units) | file |
|---|---|---|---|---|---|---|
| 0 | SYS | 0x00 | 0x20 | 0x000000–0x03FFFF (256 KB) | 0x000F | `*.sys`, header at file 0x800 |
| 1 | PCM | 0x20 | 0x30 | 0x040000–0x09FFFF (384 KB) | 0x03F0 | `*.pcm`, header at file 0 |
| 2 | USR | 0x50 | 0x30 | 0x0A0000–0x0FFFFF (384 KB) | 0xFC00 | `*.usr` (e.g. preload.bin), header at 0 |
| 3 | ALL | 0x00 | 0x80 | 0x000000–0x0FFFFF (1 MB) | 0xFFFF | 1 MB image |

Block bb (0 ≤ bb < nblocks, relative to the type) is written to flash address `(first + bb) * 0x2000`. [VERIFIED: 0x40758C–0x4075A8]
The sector mask only drives LEDs (0x406020); it does not restrict anything.

### 3.2 Set update type — `F0 42 23 58 02 tt F7` (action 2, 0x40748A) [VERIFIED]
1. tt must be < 4 and the 0x58 byte seen, else `fmt`.
2. Load nblocks/first/mask; LEDs; LCD row1 position 11 = `SYS`/`PCM`/`USR`/`ALL`.
3. **Blank scan (0x407DD6):** reads all 1 MB (8 KB blocks of 0x1000 words) and builds 0x40603C[sector] = bitmap of
   8 KB blocks that contain any word ≠ 0xFFFF. Takes noticeable time (≈0.5–1 s, INFERRED) — host waits for the reply.
4. Reply `03 00` (clears the error latch). **Nothing is erased at this point.**

### 3.3 Data block — `F0 42 23 58 04 bb 00 <packed> ss F7`

| offset | value |
|---|---|
| 0–3 | F0 42 23 58 |
| 4 | 04 |
| 5 | block number low 7 bits (must be < nblocks) |
| 6 | block number bits 7..13 — must be 00 (KORG's updater sends `(blk>>7)&0x7F`) |
| 7 … 9369 | 8192 data bytes packed into 9363 bytes (1170 groups of 8 + one group of 1+2) |
| 9370 | checksum |
| 9371 | F7 |

Packing (IPL unpacker 0x407756, KORG encoder vup 0x404A88 — identical) [VERIFIED both]:
```
pack(src[8192]):                      # host side
    out = []
    for g in range(0, len(src), 7):
        chunk = src[g:g+7]
        msb = 0
        for n, b in enumerate(chunk):
            if b & 0x80: msb |= 1 << n      # bit n -> byte n of the group
        out.append(msb)                      # MSB byte FIRST
        out += [b & 0x7F for b in chunk]
    ss = sum(out) & 0x7F                     # 8-bit sum of ALL packed bytes, low 7 bits
    return out, ss
```
IPL side: the first packed byte after the `00` is an MSB byte; then each data byte gets bit 7 = next LSB of the MSB byte;
after 7 data bytes the next byte is again an MSB byte. Exactly 8192 data bytes are stored, then the *next* byte is taken
as checksum: `(Σ packed bytes mod 256) & 0x7F`. Block number and the `00` byte are **not** in the checksum. [VERIFIED: 0x4073CE–0x40744E]
Caution: the checksum does not protect against a wrong packing convention (e.g. MSB byte last) — that would be
accepted and silently write corrupted data. [VERIFIED by construction]

### 3.4 Block write (F7 action 3, 0x407570) [VERIFIED]
```
if type >= 4:              reply 04 (hrd)
if 0x406032 != 0x58:       reply 01 (fmt)
addr = (first + bb) * 0x2000
if addr == 0:                                    # first block of SYS or ALL
    buf[0x807] = 0                               # area-ID byte of the "KORG..X" header (ALL files carry 3 here) [INFERRED purpose]
    copy buf[0x200..0x7FF] -> RAM 0x400000..0x4005FF   # flash library now = the NEW image's code!
r = write_8k(addr, 0x430000)                     # 0 ok / 1 erase failed / 4 program failed
if r != 0 (or nblocks == 0):
    mark sector failed (LED), LCD row2[sector] = '0'+r, LCD `wrt`, type := 4, reply 05
else:
    if (first+bb) & 7 == 7: LCD row2[sector] = '>'   # last 8K of a 64K sector
    if bb >= nblocks-1:  LCD row1 pos 4/6/8 = 'S'/'P'/'U' (ALL: "S.P.U" at 4)
    reply 00
```
write_8k (0x407EB2): disable interrupts (`orc #7,exr`), **erase_if_needed(addr)**, program 0x1000 words with
`fl_prog_block`, `fl_reset` (F0 + `andc #0xF8,exr`), clear SCI error flags. No read-back verify beyond DQ7 polling.

### 3.5 Erase policy (lazy, per sector) [VERIFIED: 0x407E30–0x407EB0]
erase_if_needed(addr) erases only if the blank-scan bitmap says the sector containing addr is non-blank, then marks it blank:

| addr range | sector erased | bitmap bits (8K blocks) |
|---|---|---|
| 0x0000–0x3FFF | SA0 16 KB | blocks 0–1 |
| 0x4000–0x5FFF | SA1 8 KB | block 2 |
| 0x6000–0x7FFF | SA2 8 KB | block 3 |
| 0x8000–0xFFFF | SA3 32 KB | blocks 4–7 |
| n·0x10000 (n ≥ 1) | 64 KB sector n | all 8 |

This is exactly the MBM29LV800BA / Am29LV800B **bottom-boot** map (16K, 8K, 8K, 32K, then 15 × 64K). [VERIFIED]
Consequences:
* Only sectors that receive at least one block are erased; a sector is erased when its *first-arriving* block is written,
  later blocks of that sector are programmed without erase. [VERIFIED]
* Re-sending a block of a sector that was already erased in this session programs over existing data (works only if the
  data are identical). [INFERRED]
* After any error the host must re-send Set-Type (rebuilds the bitmap from the real flash). Resuming at the failed block
  is **unsafe**: if that block is not the first block of its sector, the sector is erased again and the earlier blocks of
  that sector are lost. Restart from the first block of the sector (simplest: restart the whole type). [INFERRED from code]

### 3.6 Host sequence (KORG vup_ms2000.exe v1.3, `tfr_thread` 0x403090) [VERIFIED in x86 code]
1. Validate file (`get_file_ver` 0x402A60): "KORG" at file offset 0 or 0x800, byte 6 = 0x58, byte 7 = type 0..3,
   file size = 0x40000 / 0x60000 / 0x60000 / 0x100000. **No checksum check.**
2. Unless SkipVersionCheck: send version request, require reply mode 01; abort if file version ≤ unit version
   (type 3 ALL always passes).
3. Send Set-Type, wait for reply, Sleep(20 ms), require `03 00`.
4. For blk = 0 … size/0x2000 − 1 **in ascending order**: build packet (above), also write it to `test.dat` (debug),
   send it (midiOutLongMsg chunks of 512 bytes; TransferRate 1–3 add 330/330/500 ms between 512/256-byte chunks),
   wait for reply `03 00`, Sleep(20 ms). Any error/timeout aborts — **no retry**.
5. "Update Complete!" — **no end-of-update message is sent**; the unit is not told anything.

Receive timeout in vup: 100 ticks of a 100 ms WM_TIMER ≈ 10 s per reply. [VERIFIED: SetTimer(…,2,100) @0x403B20, 0x401DEB]
Transfer time per block at 31250 baud ≈ 3.0 s + erase/program; SYS ≈ 32 blocks ≈ 2 min, ALL ≈ 7 min. [INFERRED]

### 3.7 After the update
The IPL stays in its loop: LCD row 1 shows upper-case S/P/U for completed areas, row 2 shows `>` per completed 64 KB
sector (or an error digit). There is no reset, no watchdog, no reboot command; the user power-cycles. [VERIFIED: no
reset/WDT code in the IPL; WDT init 0xBBA is not called on the IPL path]

## 4. Flash driver library (flash 0x200 → RAM 0x400000) [VERIFIED: 0x400000–0x40028A]

16-bit bus: command addresses are byte addresses 0xAAAA (word 0x5555) and 0x5554 (word 0x2AAA).

| entry | target | function |
|---|---|---|
| 0x400000 | 0x400020 | autoselect: AA/55/90, read @0 and @2, returns (manuf_lo<<8 | dev_lo), then reset — not used by IPL |
| 0x400004 | 0x400052 | reset/read-array: F0 @AAAA; `andc #0xF8,exr` |
| 0x400008 | 0x400066 | `orc #7,exr` |
| 0x40000C | 0x40006C | sector erase: AA,55,80,AA,55 then 30 @er0; poll: call 0x40001C, DQ7=1 → ok; DQ5=1 → re-read DQ7 → fail if 0; r0l = 0 ok / 1 fail |
| 0x400010 | 0x4000C2 | program one word r1 @er0 (AA,55,A0), DQ7/DQ5 poll — not used by IPL |
| 0x400014 | 0x400102 | program e2 words (1…0x8000) from @er1 to @er0, per word AA,55,A0, data, DQ7/DQ5 poll (calls 0x40001C) ; r0l = 0 ok / 1 fail |
| 0x400018 | 0x40015A | read-modify-write of whole **64 KB** sectors through RAM 0x430000 (assumes uniform 64K sectors — wrong for sector 0) — **not used by the IPL** (main firmware only, INFERRED) |
| 0x40001C | 0x4001FC | poll callback: LED refresh every 16 calls |

There is no software timeout: erase/program completion relies on DQ7/DQ5 only (a chip that never reports DQ5 would hang
the IPL). Programming success is judged only by DQ7 polling; no read-back compare. The IPL uses entries 04, 08, 0C, 14 only.
[VERIFIED: grep of `jsr 0x4000xx` in IPL]

## 5. Brick risk

1. **SYS and ALL updates rewrite the boot sector SA0 (0x0000–0x3FFF)**, which holds the vector table, the flash
   library (0x200), the reset/boot classifier (0x810–0xD53) and the IPL image itself (0xD54–0x1DD6) plus the launcher
   (0x1CB2). There is no protection, no second copy, no "update in progress" flag, no image checksum check.
   [VERIFIED: write path has no address restriction; boot path does no integrity check]
2. Brick window (in-order transfer as KORG does it): from the SA0 erase triggered by **block 0** until block 0
   (0x0000–0x1FFF) is fully programmed (≈ one sector erase ~0.7–several s + 4096 word programs). Everything the
   boot→IPL path needs lies in 0x0000–0x1DD6 (vectors, 0x200–0x48A, 0x810–0xD53, 0xD54–0x1DD6), so once block 0 is
   written the unit can re-enter IPL even if the rest of the update is lost. [VERIFIED addresses; INFERRED conclusion]
   Block 1 (0x2000–0x3FFF) is erased together with block 0 (same 16K sector); losing it only breaks the main firmware.
3. **Out-of-order sending is dangerous:** any block in 0x0000–0x3FFF (block 0 or 1 of SYS/ALL) that arrives first
   erases SA0. If block 1 is sent before block 0, the boot code is gone until block 0 arrives. Always send block 0 first
   (then ascending). [VERIFIED erase logic]
4. While writing block 0 the IPL **switches to the flash library contained in the new image** (buf 0x200–0x7FF copied to
   RAM 0x400000 before write_8k). If that code is not a compatible library (wrong file, wrong type, corrupted packing),
   the IPL jumps into garbage *before or during* the SA0 erase → brick. The host must guarantee that block 0 is a
   genuine system image (validate header "KORG" at 0x800, 'X', type 0 (or 3 for ALL), size, and compare 0x200–0x48A
   with a known-good library). [VERIFIED: 0x4075AE–0x4075C4, 0x407F42]
5. If a write error happens in block 0 and power is still on, the IPL (running from RAM) is still usable: re-send
   Set-Type (rescan) and block 0 again. Do **not** power-cycle before block 0 succeeded. [INFERRED]
6. Interrupts: the flash library unmasks interrupts (`andc #0xF8,exr`; SYSCR=0x21 → interrupt-control mode 2). All
   vectors point into flash (0x2108, 0x41F2, 0x4386, NMI = 0x2108). No interrupt source appears to be enabled on the IPL
   path (SCR1 = 0x30, TIER = 0x40 only), but an NMI or a stray enabled source during an SA0/block-1 erase would
   vector into erased flash. [INFERRED — check in emulator]
7. sci_error (0x4072B2) writes SSR1 = 0, which also clears TDRE and may transmit a stale TDR byte. Harmless. [INFERRED]
8. The IPL accepts any data for any type; it does not check that a SYS file is sent with type 0. All validation is
   host-side. [VERIFIED]
9. Word checksum: the 16-bit big-endian word sum of the SYS area (0x00000–0x3FFFF) and of the PCM area
   (0x40000–0x9FFFF) is 0x0000 in both x811v107.sys and flash.bin (the word at header+0x0E balances it); the USR
   area / preload.bin sum is 0x5DA4 (different scheme or range). Neither the IPL nor vup checks it; whether the main
   firmware checks it at boot is [UNKNOWN]. A patched .sys should re-balance word 0x80E to keep the sum 0 (cheap
   insurance). [VERIFIED sums; consequences UNKNOWN]

## 6. Command 1 and the unknown-technologies patch (fwpatch + combine.c)

v1.07: cmd 1 → 0x40730E = format error (`03 01`, latch set). [VERIFIED: table word at flash 0x1CE0 = 0x0040730E]

Handler calling convention: state 4 does `jmp @er0` right after the command byte, so the handler owns the SCI from

Notes / defects:
* fwpatch.asm's comment "set 0x407F8A = 0x408084" is wrong (0x407F8A is inside entry 0); combine.c patches the correct
  slot 0x407F8C. [VERIFIED]
* combine.c does not fix the word checksum at 0x80E (see §5.9) and does not bound-check patch_size. [VERIFIED]
* Installing the patched .sys **is** a SYS update → it goes through the full brick window of §5 (block 0 rewritten).
* Dump request (as fwpatch/fwdump implement it): `F0 42 23 58 01 A2 A1 A0 Am N2 N1 N0 Nm F7` — big-endian 24-bit address
  and size, each as 3 bytes with bit 7 removed followed by an MSB byte (bit0 → first byte, bit1 → second, bit2 → third).
  Note this is the opposite order to the IPL's own packing (MSB byte first). The trailing byte is swallowed unchecked.
* Dump reply: `F0 <packed data> F7`, no KORG header; packing = 7 data bytes followed by their MSB byte (bit n = byte n),
  final partial group followed by its MSB byte. LCD shows `DUMPING`, then row 2 is reset to dots.
* fwpatch's range guard `cmp.l #0x100000,er1 / bhi` lets one byte at 0x100000 be read (off by one, harmless read).
* fwpatch writes TDR1 directly and uses TX-ring bytes 0x40624C–0x406250 as scratch. If the ring holds unsent bytes
  (e.g. F8 heartbeats while the error latch is set) they may be corrupted / sent after the dump. Before dumping, make
  sure the latch is clear (a successful Set-Type clears it and erases nothing). [INFERRED]
* While the dump runs the main loop is stopped (no tick, no F8); RX errors during the address phase go to sci_error.
